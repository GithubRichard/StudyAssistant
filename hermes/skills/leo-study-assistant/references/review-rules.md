# 错题二次复查规范（服务端执行版）

适用于业务后端在首轮批改结果通过协议校验之后：把判错题与存疑题交给配置的复查模型
（第二个模型）独立复查。**复查由服务端编排与核验，技能不执行、不自述。**

## 0. 运行前提与身份核验

- 复查模型由服务端配置（`hermes.review_model`）：
  - `model_routes` **别名**（如 `glm`）可只写 `model`；
  - **底层模型 ID**（如 `glm-5.3`）必须同时写 `provider`（如 `zai`）——
    只给 `model` 不给 `provider` 会被网关静默忽略，回落全局默认模型；
  - GLM-5.3 系列的 `reasoning effort` 只接受 `low / high / max`，`medium` 会被上游拒绝；
  - 别名对应的期望底层身份写在 `review_expected_model` / `review_expected_provider`，
    **声明性配置，不是调用成功的证据**。
- 身份核验以网关**报告**的模型为准：报告缺失记「身份未确认」；报告与首轮相同模型记「路由不符」。
  只有报告身份与配置期望一致、且不同于首轮模型，本次复查才算成立。
  请求值不得冒充实际值；身份不成立时本次复查按失败如实标注，不采纳其逐题结论。
- 复查失败不影响首轮成果：归档、台账、历史记录照常写入，复查字段如实标注。
- 不自动重试；不得用其他模型冒充指定复查模型。

## 1. 谁进入复查

- 复查对象是首轮判为 `wrong`（判错）与 `uncertain`（存疑）的题。
- `unanswered`（未作答）不送复查，避免把没作答的题当错题；也不得为凑数改判。
- 没有判错题与存疑题时跳过（`review_summary.state = not_required`）。
- 超过单次上限（`review_max_questions`，默认 30）时判错题优先，未送审题如实标 `unprocessed`。
- 补充材料后的新一轮执行会**重新复查**当前全部候选题（不复用上一轮结论，
  以覆盖补图、转录修正与上轮失败的情形），每轮仍最多一次复查调用。

## 2. 传给复查模型的材料（纯文字核查，不读图）

- 每道送审题分两节呈现：
  - 【提取转写】：提取阶段模型从作业原图读出的题干、学生作答（只转写、未判定）；
    字迹存疑的题在转写备注里说明。
  - 【首轮批改结论】：另一模型基于转写独立求解、比对后给出的首轮判定、参考答案、
    解题步骤、错因、知识点与判定证据，仅供核查，不是标准答案。
- **不提供任何图片**：复查方不得查看、还原或猜测原图内容，只能依据文字转录
  核查逻辑与计算；转写缺失、字迹存疑导致信息不足的题标 `unverified`，不要猜测。
- 只读约束写在提示词中，但**提示词不是权限控制**：启用前须在真实环境核实复查会话的工具隔离。

## 3. 复查方职责

- 复查输出协议独立于学习结果：每道送审题返回 `id` + `state`（`agreed` / `disagreed` / `unverified`）
  + `note` + `basis`；`disagreed` 必须给可核验依据。
- 重点检查：转写与首轮结论是否自洽（如学生作答明明与参考答案一致却被判错）、
  首轮求解步骤是否有计算或推理错误、是否遗漏了转写中的条件、
  是否把合理答案误判为错、错因是否有文字证据支撑。
- 存疑题的 `agreed` 仅表示未发现对存疑判断的异议，**不代表题目已确认正确或疑点消除**。
- 无异议的题只标「未发现异议」，不重复整套解析，也不等同于证明原判定必然正确。
- **不做二选一、不作最终裁决、不覆盖主流程结论**；不使用「正确／错误」给学生重新定性。
- 不得返回未送审的题，不得漏题、不得重复；服务端按送审 id 集合对账，
  漏题/未知 id/重复 id/非法状态的响应整体拒绝（送审题标 `unverified`）。

## 4. 服务端处理复查结论

- 合并只写 `review` / `review_summary` 等服务端管理字段：
  `status`、作答、答案、步骤、`remediation`、`retests` 原样保留——**复查异议不改判**。
- `review.state=disagreed` 时在 `final_decision_basis` 追加「[服务端二次复查记录到异议，尚未重新裁决]」
  与复查依据，保留首轮依据；`final_decision` 不变。
- 计数（scope / disagreed / unverified / target_count / unprocessed）只由服务端计算，
  不采信复查方自报的汇总。
- 首轮模型自述的 `review` / `review_summary` 一律被服务端规范化覆盖：
  未配置 → `not_run`；无候选 → `not_required`；失败 → `failed`；全部覆盖且有明确结论 → `completed`；
  存在超限、漏题或无法核查 → `partial`。纯转写核查（`coverage=transcript_only`）
  是设计如此，不降级，如实备注「未读取原图」。
- 合并后的完整结果再次通过协议校验；不通过则退回规范化基线并把复查标为失败，
  **不把非法数据写库，也不恢复首轮自称已复查的字段**。
- 服务端把「二次复查记录」附记随本轮归档一次写入，与结果 JSON 同源；
  归档正文与结构化字段保持一致。
- 复查不产生订正/复测事件，也不改变台账状态；「已复核」不代表已掌握。
